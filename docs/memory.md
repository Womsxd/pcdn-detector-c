# 内存占用与低内存优化

本工具针对低内存路由器做了专门优化。内存主要由三部分构成：**内核抓包环形缓冲**、
**进程自身（代码段 / 线程栈 / libc 堆）**、**用户态检测数据结构**。

与 Go 版本最大的区别：C 版本**没有 GC**，因此 `[memory] memory_limit` / `gc_percent` 只为
兼容既有配置而保留——会被解析和校验，但不产生运行时效果（配置后启动日志会给出提示）。
真正决定内存上限的是下面这些项：`frame_size` / `block_size` / `num_blocks` / `snaplen`、
`low_memory`、`peer_limit`、`max_ports`。

## 内核抓包缓冲（AF_PACKET + TPACKET_V2）

环形缓冲总内存 = `block_size × num_blocks`，默认 **256KiB**（`65536 × 4`）。

- `frame_size`：单个帧（槽位）上限（字节），须能整除 `block_size`，默认 2048；
- `block_size`：每个块大小（字节），须为页大小(4096)与 `frame_size` 的整数倍，默认 65536；
- `num_blocks`：块数量（≥ 1），默认 4；
- 帧槽数 = `(block_size / frame_size) × num_blocks`，默认 `32 × 4 = 128` 个。
  TPACKET_V2 下**每个帧最多承载一个报文**，因此帧槽数就是可缓冲的报文数。
- 上述参数非法（不能整除、非页大小整数倍等）时**整体回退到内置默认值**；启动日志会输出实际生效值，
  例如：

  ```
  抓包缓冲：frame=2048B，block=65536B × 4 块 = 256KiB，snaplen=256B（可在 [capture] 中调整）
  ```

## 内核层 snaplen（收益最大之一）

内核 BPF 放行时返回 `snaplen`，内核只把每个报文的**前 `snaplen` 字节**复制进环形缓冲
（默认 **256B**），负载不再进入用户态。解析只读以太网头 + IP 头 + 扩展头 + 4 字节端口，因此：

- 流量统计取内核记录的线路长度（`tp_len`），**不受截断影响**；
- 小核上的内核复制量从整帧降到约 256B，CPU 与内存带宽明显下降；
- 代价：若某报文的传输层头落在 `snaplen` 之外（超长 IPv6 扩展头链），该包会被跳过。

取值规则：`snaplen <= 0` 用默认 256；`< 64` 自动抬到 64；`> frame_size` 自动压到 `frame_size`。
默认 256B 覆盖常见场景；如有特殊需要可调大，或设为与 `frame_size` 相同以恢复整帧复制（旧行为）。

## 内核层 BPF 过滤（收益最大）

启动时给抓包 socket 附加经典 BPF 过滤器，只放行**可能承载所选传输层协议的 IPv4/IPv6 报文**
（兼容 VLAN / QinQ）。ARP、STP、IPv4 ICMP/IGMP、IPv6 ICMPv6/NDP 等无关报文在**内核环形缓冲之前**
即被丢弃，不再复制到用户态。

- 由 `[capture] protocol` 控制（**默认 `"udp"`**）：`"udp"` 仅放行 UDP、`"tcp"` 仅放行 TCP、
  `"all"` 同时放行 UDP 与 TCP。`"all"` 时该过滤器是解析逻辑的**严格子集**，被丢弃的报文
  原本也会被丢弃，不改变检测语义。
- 非首片报文（没有传输层头）不会被当作 UDP/TCP 解析：IPv4 在内核层按分片偏移直接丢弃；
  IPv6 分片放行后由用户态检查 Fragment 偏移并丢弃非首片。
- `"udp"` / `"tcp"` 时另一种协议不再参与统计，防火墙封禁的协议也随之变化。

## 用户态检测数据结构

数据结构用 uthash 实现，按「设备 → 地址族 → 端口 → 对端」四级组织：

- **对端键紧凑**：IPv4 用 **4 字节**、IPv6 用 **16 字节**原始地址作为哈希键（不同地址族分属不同
  端口表，键里不需要地址族标记），而不是保存 IP 字符串。
- **对端记录只保留必要字段**：键 + 最近出现时间（`int64` 纳秒）+ 「已提示」标记 + 哈希句柄。
  字节数只在**端口级**累计（`up_bytes` / `down_bytes`），对端级不重复保存。
- **告警期标记复用对端记录**：告警期间「已提示对端」直接打在对端记录的 `reported` 标记上，
  只额外维护一个计数，不再单独维护一份与对端集合同规模的集合。
- **地址族拆表**：端口表按 `device.v4` / `device.v6` 拆成两张，IPv4 端口条目只需 4 字节键，
  各地址族的统计与遍历逻辑各自独立，互不影响。
- **端口 / 对端及时回收**：端口内对端全部过期且不在告警中时，整个端口状态（含哈希表）被删除；
  设备无端口时同样删除。
- **哈希表收缩**：uthash 删除元素后不会自动缩小桶数组。每次扫描记录设备 / 端口 / 对端三级
  哈希表的元素数峰值，当当前元素数降到峰值 **1/4 以下**（且峰值 ≥ 64）时重建该表，
  把多余桶还给分配器。该机制仅对「峰值大、当前小」的表触发，避免抖动。
- 抓包层直接由报文原始字节构造地址，**每个报文不分配 IP 字符串**；IP 只在打印告警与 HTTP API
  返回时按需格式化（告警日志最多列出 20 个 IP，其余以省略提示）。

### 单设备端口条目上限（`[memory] max_ports`，或命令行 `--max-ports`）

`peer_limit` 只限制单个端口内的对端数，端口条目本身也需要上限：目的端口扫描、QUIC / TCP 短连接
会为每个新端口建立入口，65536 个端口足以在小内存设备上造成压力。

- 取值：省略时默认 **512**；`0` 表示**不限制**。
- 达到上限时**批量提前过期**当前端口数的 10%：先按「距过期窗口的剩余寿命」把端口按窗口均分
  10 档（0 档 = 最接近过期），同档内按对端数升序，再按最近活动时间 / 端口号排序。批量淘汰把
  全表排序的开销摊到每 10% 新端口上，避免每个新端口都全表排序被扫描流量当成 CPU 放大器。
- **告警中的端口不参与淘汰**（否则会打断续期、结束回调与解封）；若全部端口都在告警中，
  则新端口不建立、该端口流量不再累计，首次丢弃会输出日志提示。
- 上限被热更新调小时，下一次扫描会把超出的端口收敛到新上限。
- 可观测：`/api/v1/devices` 顶层的 `port_evictions` / `port_drops` 为累计计数（提前过期端口数 /
  丢弃的新端口报文数）。
- 与 `peer_limit`、`low_memory` 相互独立，三者可同时启用。

### 单端口对端记录上限（`[memory] peer_limit`，或命令行 `--peer-limit`）

为每个「设备 + 端口」的对端统计设置上限，防止单个端口在窗口内记录无限多的对端而占用大量内存。
达到上限后**不再记录该端口的新对端 IP**（已有对端仍照常刷新，端口级流量仍完整累计）。

- 取值：省略该项时默认取 `max(1000, threshold × 10)`；**开启低内存模式（`low_memory = true`）时
  默认改为 `threshold`**；`0` 表示**不限制**；大于 `0` 但小于 `threshold` 时**自动提升为
  `threshold`**，以保证仍能达到触发阈值。显式配置的 `peer_limit` 始终优先。
- 代价：达到上限后该端口不再输出其新增的对端 IP（「相关IP」与「持续产生PCDN行为」中的
  新增 IP 均受此上限约束）。
- 热更新：reload 时按新的 `threshold` / `low_memory` / `peer_limit` 重新计算生效上限。阈值调高
  会同步抬升默认上限，否则端口永远记录不到阈值个对端、告警会静默失效。

### 低内存模式（`[memory] low_memory`，或命令行 `-L` / `--low-memory`）

内存极度受限、且只关心「是否触发 PCDN」而不关心具体对端时启用。某「设备 + 端口」一旦达到
阈值触发告警，即**清空已记录的对端 IP 列表**（释放整张对端哈希表）并**不再记录该端口的
新对端 IP**，只保留触发状态（告警续期、累计流量、累计对端计数）继续统计：期间仍有流量则续期，
超过 `alert_duration` 无流量则输出「PCDN行为结束」；结束后恢复正常统计，可再次触发。

- 代价：该端口告警期间不再输出「持续产生PCDN行为（新增相关IP）」，也不展示持续新增的对端
  IP；首次告警日志仍会输出触发时窗口内的**完整对端 IP 列表**。
- 效果：触发后该端口的对端统计不再随对端数量增长，避免长期告警（滑动续期）时内存持续攀升。
- 另外：未显式配置 `peer_limit` 时，其默认值会由 `max(1000, threshold × 10)` **收敛为
  `threshold`**，进一步压低**触发前**的对端内存。

> 抓包协议也可用命令行 `-P` / `--protocol` 指定（`udp` / `tcp` / `all`），优先级高于配置文件。
> 缓冲（`frame_size` / `block_size` / `num_blocks` / `snaplen`）、`memory_limit` 与 `gc_percent`
> 暂无对应命令行参数，请通过配置文件调整。

## 抓包缓冲与 snaplen（默认配置方案）

### 默认值

| 配置项 | 默认值 | 约束 / 说明 |
| --- | --- | --- |
| `snaplen` | `256` | 内核层 BPF 每包复制到用户态的最大字节数（BPF 返回值） |
| `frame_size` | `2048` | 单个帧上限，须能整除 `block_size` |
| `block_size` | `65536` | 每个块大小，须为页大小(4096)与 `frame_size` 的整数倍 |
| `num_blocks` | `4` | 块数量（≥ 1） |
| 环形缓冲合计 | **256KiB** | `block_size × num_blocks`，默认 128 个帧槽 |

### 为什么是这套值

1. **snaplen 是主要收益**：BPF 放行时返回 `snaplen`，内核只把每个报文的前 `snaplen` 字节
   复制进环形缓冲，负载不再进入用户态。解析只需要以太网头 + IP 头 + 扩展头 + 4 字节端口，
   256B 足以覆盖「2 层 VLAN + IPv6 + 分片 + 若干扩展头」的常见组合（约 90B）。
2. **流量统计不受影响**：报文长度取内核记录的线路长度 `tp_len`，与截断后的复制长度
   `tp_snaplen` 相互独立，因此字节数统计与检测阈值保持原语义。
3. **块大小影响分配成功率**：64KiB 块是 order-4 分配，旧的 256KiB 块是 order-6，
   在碎片化内存上更容易成功。
4. **帧槽数才是突发容量**：TPACKET_V2 每帧只能放一个报文，默认 128 个槽。`frame_size` 保持
   2048（需容纳内核头部与 snaplen，过小会被内核拒绝）；需要提高突发容量时增大 `num_blocks`。

### 预设组合（按内存与流量选择）

`[capture]` 的 4 个键决定抓包缓冲与每包复制量。一般**只需挑一个预设**替换这 4 行，
`interface` / `promisc` / `protocol` 保持不变：

| 预设 | 适用场景 | `frame_size` | `block_size` | `num_blocks` | `snaplen` | 环形缓冲 | 帧槽数 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 最小 | 32/64MB 内存、百兆以内 | 2048 | 65536 | 2 | 256 | 128KiB | 64 |
| **普通（默认）** | 大多数家用路由器 | 2048 | 65536 | 4 | 256 | 256KiB | 128 |
| 高流量 | 千兆、小包多、担心丢包 | 2048 | 65536 | 8 | 256 | 512KiB | 256 |
| 超高流量 | 千兆满载 / 多 WAN 汇聚 | 2048 | 65536 | 16 | 256 | 1MiB | 512 |
| 旧版默认 | 需要整帧复制 / 沿用旧配置 | 65536 | 262144 | 8 | 65536 | 2MiB | 32 |

例如切换到「最小」：

```toml
[capture]
interface = "br-lan"
promisc = true
protocol = "udp"

frame_size = 2048
block_size = 65536
num_blocks = 2
snaplen = 256
```

### 单项调整

| 目标 / 现象 | 调整 |
| --- | --- |
| 高 pps（千兆满载、小包为主）怀疑丢包 | `num_blocks` `4 → 8`（512KiB）`→ 16`（1MiB） |
| 出现超长 IPv6 扩展头链导致漏检 | `snaplen` `256 → 512 / 1024`（同时确认 `frame_size` 足够） |
| 需要完整载荷（临时抓包排查） | 把 `frame_size` 与 `snaplen` 同时调大（如 `4096 / 4096`） |
| 内存极度紧张 | `num_blocks = 2`（128KiB），并配合 `[memory] low_memory` |
| 只想降 CPU / 带宽、不在意缓冲 | 保持默认，不要动 `frame_size` |

### 从旧默认迁移（注意行为变化）

- **未配置 `snaplen` 时自动取 256**：升级后即启用截断。这是相对旧版本的唯一行为变化——
  统计与告警语义不变，但**传输层头超出 256B 的报文会被跳过**（极端 IPv6 扩展头链）。
- 旧的环形缓冲参数（`frame_size = 65536`、`block_size = 262144`、`num_blocks = 8`）仍然合法，
  但会占用 2MiB，不再享受本次优化的内存收益。
- 需要恢复「整帧复制」时，必须**同时**满足 `snaplen = frame_size`：只把 `snaplen` 设成
  65536 而 `frame_size` 还是 2048 时，snaplen 会被压到 2048。
- 热更新：`snaplen` / `protocol` / `promisc` 在既有 socket 上重设 BPF，不重开 socket；
  `frame_size` / `block_size` / `num_blocks` / 网卡变化会重开 socket（重开期间可能有极短丢包）。

### 验证方式

- 启动日志（`[log] level = "info"`）会打印实际生效的 `frame` / `block` × 块数 / `snaplen`
  与内核过滤器放行的协议，可用来确认参数是否被接受（非法值会回退默认）。
- `make test` 覆盖配置解析与检测器阈值 / 对端上限 / 端口上限 / 淘汰逻辑。
- 运行期内存可从 `GET /dev/memory` 的 `rss_bytes` / `vm_bytes` / `threads` 观察；
  数组（环形缓冲）只在启动或重开 socket 时体现，`rss_bytes` 包含其驻留页。
- 环形缓冲丢包计数目前**未通过接口暴露**；`ip -s link` 反映的是网卡层丢包，不等于
  AF_PACKET 环形缓冲溢出。如需判断，可临时把 `num_blocks` 加倍，观察检测结果/CPU 是否变化。
